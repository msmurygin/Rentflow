# RentFlow — Product & Engineering Specification v0.1

**Дата:** 17 октября 2026  
**Статус:** Draft → ready for implementation spike  
**Цель:** быстро выпустить рабочий продукт с первым реальным сценарием «арендатор прислал фото счётчиков → собственник одобрил расчёт → арендатор получил сумму».

> **Product principle:** RentFlow — система начислений и расчётов между арендатором и собственником, а не полноценная PMS. Начинаем с одной квартиры через Telegram, проектируем ядро так, чтобы позднее добавить управляющих, пакетный импорт и новые страны.

## 1. Решаемая проблема

Сейчас арендатор отправляет фотографии счётчиков в Telegram. Собственник вручную извлекает текущие показатели, находит прошлые, рассчитывает расход и сумму по договору, пишет арендатору. Арендатор самостоятельно оплачивает выставленную сумму. Для нескольких квартир процесс превращается в ежемесячное сведение данных из сообщений, квитанций и таблиц.

**Начальный договорный кейс:** арендатор оплачивает **воду и электроэнергию по счётчикам**. Прочие статьи (водоотведение, капремонт, уборка, содержание, отопление и т. д.) отключены для арендатора до явной настройки. Отдельные начисления за воду/ГВС и тарифы требуют подтверждения при настройке; не выводить тарифы из догадок.

### Измеримый результат
- От фото до черновика расчёта без ручного переноса показаний (кроме исправления ошибок).
- Собственник может проверить источник каждой цифры и отправить расчёт одним действием.
- История показаний/начислений воспроизводима; дубли не создают повторные начисления.
- При ошибке распознавания нельзя незаметно выставить неверный счёт.

## 2. Аудитории и развитие

| Сегмент | Первое обещание | Канал | Монетизация — гипотеза |
|---|---|---|---|
| Частный собственник (1 квартира) | Не считать коммуналку руками | Telegram | Бесплатный базовый план |
| Собственник (2–10 квартир) | Напоминания, история, контроль оплат | Telegram + web | 9 €/мес. до 5 объектов — проверить |
| Управляющий (10–100+ объектов) | Массовые начисления и управление исключениями | Web + файлы + API | 39–99 €/мес. — проверить |
| Арендатор | Понятный расчёт и доказательства | Telegram + личная ссылка | Бесплатно |

**Не обещать €5–20k MRR как результат релиза.** Эта цель требует проверки спроса, повторного использования и стоимости привлечения.

## 3. Scope: релиз R0 — Telegram-first MVP

### Обязательно (P0)
1. Регистрация собственника через Telegram, создание одного объекта, привязка одного арендатора по invite-token (срок действия, одноразовость).
2. Создание счётчиков: холодная вода, горячая вода, электричество; поддержка произвольного типа для следующих релизов. Уникальный идентификатор каждого счётчика и единицы измерения.
3. Стартовые показания с датой + тарифы с датой действия. Для двухтарифной электроэнергии и специальных тарифных формул — отдельное расширение; в R0 явно только один тариф на счётчик.
4. Бот запрашивает фотографии; арендатор отправляет несколько фото, система привязывает показание к счётчику, показывает распознанное число и просит подтверждение.
5. Зафиксировать фото-оригинал, извлечённое значение, подтверждённое значение, время получения, кто подтвердил, confidence/причину ручной корректировки.
6. Проверка: показание не отрицательное; текущее обычно >= прошлого; подозрительный скачок требует ручной проверки. Замена/обнуление счётчика — вручную через отдельную корректировку, не авторасчёт.
7. Детерминированный расчёт: объём = текущее − предыдущее; стоимость = объём × действующий тариф. Денежная арифметика decimal или целые минимальные единицы, не float. Выбранные тарифы и формулы фиксируются в снимке расчёта.
8. Собственник видит проект расчёта и может «подтвердить / исправить / отклонить»; **до подтверждения счёт арендатору не отправлять**.
9. Telegram-сообщение с расшифровкой и итогом; состояние «ожидает оплаты»; кнопка «отметить оплачено» у собственника. В R0 **нет автоматического списания, проверки банка и утверждения, что фактическая оплата подтверждена провайдером**.
10. Минимальная история периодов и расчётов, защита от повторного нажатия и дублированного Telegram update.
11. Русский интерфейс; приватность: каждый участник видит только свои объекты/счета; запрет выдавать документы по угаданному URL.

### Следующий релиз R1 (после пользователей)
- Web-портал арендатора с magic link и историей начислений/платежей.
- Настраиваемые услуги: по показанию, фикс, сумма из квитанции, процент, полностью собственник, полностью арендатор, смешанное распределение.
- Автоматическое напоминание о сроке показаний и просрочке подтверждённого начисления; ограничение частоты и возможность отключения.
- Загрузка PDF/фото квитанций, извлечение начислений с ручной верификацией.
- Несколько объектов, роли собственника и управляющего.

### R2: управляющие
- XLSX/CSV массовая загрузка объектов, арендаторов, счётчиков, начальных показаний и начислений; предварительный просмотр, проверки, отчёт по ошибкам, идемпотентный upsert.
- Пакетная обработка документов, очередь исключений, массовое подтверждение только безопасных начислений.
- Импорт банковской выписки и сопоставление платежей с начислениями (не угадывать при неоднозначности).
- Календарь платежей, частичные платежи, переплаты, долги, корректировки.
- Audit trail по ролям и объектам; экспорт данных.

### R3: интеграции / международный рынок
- Адаптеры источников: email forwarding, file ingestion, разрешённые API поставщиков, импорты из PMS.
- Платёжные ссылки и статусы через локальных PSP (возможные кандидаты: Яндекс Пэй и другие для РФ, Stripe/SEPA-подобные провайдеры в доступных юрисдикциях). **Доступность и право обслуживать соответствующих получателей проверять до обещаний клиенту**.
- Локальные templates по странам: валюта, язык, периоды, законодательные правила начислений, защита данных, хранение.
- White label / API; акты въезда-выезда, депозит, dispute management; Tenant Passport — только opt-in.

### Вне MVP
Автоматический вход в Госуслуги/mos.ru/Мосэнергосбыт с паролями пользователя; автоматическая отправка показаний; автоматические списания; банковская лицензируемая деятельность; полноценная бухгалтерия и управление ремонтами; локальные LLM; микросервисная платформа; собственный дизайнер UI.

## 4. Пользовательские сценарии (R0)

**US-01 Настроить квартиру:** собственник создаёт объект, выбирает валюту RUB, создаёт три счётчика, начальные показания, тарифы и назначает арендатора. Система не разрешает расчёт без стартовых значений и тарифа.

**US-02 Сдать показания:** арендатор получает запрос, загружает фото; если фото содержит несколько чисел, неоднозначно или плохо читается — указывает нужное значение вручную. Система показывает предыдущее значение и текущий результат для подтверждения.

**US-03 Рассчитать:** система выбирает два подтверждённых последовательных показания каждого счётчика, вычисляет расход и сумму. Если отсутствует фото/показание хотя бы обязательного счётчика, расчёт остаётся неполным.

**US-04 Согласовать:** собственник видит строки с формулами и ссылками на фото, подтверждает итог. В Telegram арендатор получает текст расчёта и номер периода. Повторная доставка одного сообщения не создаёт повторную сумму.

**US-05 Оплата:** жилец платит вне системы; собственник отмечает факт получения денег. Статус и время меняются, сохраняется запись аудита. Позже — банковская сверка.

**US-06 Исправление:** после выставления счета обнаружена ошибка. Существующий счёт не редактируется молча: он аннулируется или получает связанную корректировку с причиной, затем формируется новый расчёт.

## 5. Доменная модель (имена предлагаемые, не существующие сущности Quark)

- `account` — собственник/управляющая организация, `id`, locale, timezone.
- `user` — Telegram identity и роль в рамках аккаунта; связь tenant ↔ property ограничена периодом аренды.
- `property` — объект, адрес/название, страна, валюта, timezone.
- `tenancy` — арендатор, объект, даты, статус, contractual billing policy.
- `meter` — тип, serial/label, unit, installed_at, active, property_id.
- `meter_reading` — meter_id, value DECIMAL, read_at, submitted_at, photo_id, source, confirmed_by, status, revision.
- `document` — storage key, SHA-256, mime, retention policy, original name, uploader.
- `tariff` — meter/service, money per unit, currency, valid_from/valid_to, source.
- `charge_rule` — услуга, плательщик, способ расчёта, договорная версия, effective dates.
- `billing_period` — property/tenancy, start/end, state; уникальное правило выставления по периоду и договору.
- `bill` + `bill_line` — неизменяемый снимок входов, расхода, тарифа, суммы, источника, состояния, версии расчёта.
- `payment_record` — сумма, дата, source (`owner_marked` в R0), reference, status; **фактический статус провайдера отдельно в R3**.
- `audit_event` — actor, action, object, before/after metadata, timestamp.
- `outbox_event` — надёжная отправка Telegram уведомлений после коммита транзакции.

**Конвенции:** UTC timestamps с локальным display timezone; monetary amount + currency; показания decimal; строгая tenant isolation; primary keys UUID; хранение тарифов/правил versioned. Контрактный долг ≠ долг перед ЖКХ: не объединять эти величины.

## 6. R0: расчёт и инварианты

```text
for each required meter in billing period:
  prev = last confirmed reading before period end / previous boundary
  curr = confirmed reading for current period
  require prev, curr and valid meter continuity
  usage = curr.value - prev.value
  require usage >= 0 or explicit meter replacement adjustment
  tariff = effective tariff for relevant consumption period
  require tariff present, currency compatible
  amount = round_currency(usage * tariff)
bill.total = sum(line.amount)
```

- Определить **единое правило дат**: показания относятся к дате фактического снятия; нельзя автоматически считать месяц полным, если периоды чтения различаются.
- При смене тарифа внутри периода: R0 переводит случай в ручное подтверждение/разбиение интервала, не применяет молча один тариф ко всему расходу.
- Нулевой расход разрешён; отрицательный/аномальный расход — исключение.
- Единственная финальная версия начисления на `(tenancy, period)`; коррекции явные и аудируемые.
- Нельзя использовать LLM для вычисления итоговой денежной суммы: LLM/OCR выдаёт candidate + confidence, core валидирует, человек подтверждает.
- Идемпотентность Telegram webhook `(bot_id, update_id)` и команды «подтвердить расчёт».

## 7. Техническая архитектура

**Цель — один Rust backend (modular monolith), PostgreSQL и Telegram bot.** Не использовать весь стек Quark как обязательную зависимость.

```text
Telegram Bot/Webhook ──> Rust API / workflow handlers
                                 |
                        Domain application services
                          /       |        \
                    Metering   Billing   Notification
                          \       |       /
                        PostgreSQL + Outbox
                                 |
                     Worker (OCR + message delivery)
                                 |
                   Object storage (encrypted photos)
```

Предлагаемые библиотеки (подтвердить версиями при scaffold): `axum`, `tokio`, `sqlx`, `teloxide` либо прямой Telegram Bot API, `rust_decimal`, `serde`, `tracing`; миграции SQL. Хранилище изображений — S3-compatible или локальное на пилоте с планом миграции. OCR: внешний vision API через `ReadingExtractor` trait; **ручной ввод как обязательный fallback**. Предпочтителен один deployable + фоновый worker, без Kafka/Kubernetes.

`ReadingExtractor` contract:

```json
{
  "candidates": [{"meter_hint":"cold_water","value":"125.341","unit":"m3","confidence":0.94}],
  "requires_review": true
}
```

Это пример структуры, а не гарантированная точность или спецификация конкретной модели. Не отправлять чувствительные фотографии в неподтверждённый сервис без согласия и политики обработки.

## 8. API / события (черновые контракты)

- `POST /v1/properties` — create object.
- `POST /v1/properties/{id}/meters` — register meter with initial reading.
- `POST /v1/invites` — scoped tenant invite.
- `POST /v1/meter-readings` — submit/confirm reading (requires object-level authorization).
- `POST /v1/billing-periods/{id}/calculate` — produce idempotent draft or validation errors.
- `POST /v1/bills/{id}/approve` — atomically approve current version + outbox event.
- `POST /v1/bills/{id}/mark-paid` — record manual payment attestation.
- `GET /v1/bills/{id}` — bill details, photos (authorized signed URLs), audit.
- `POST /telegram/webhook` — signed/secret-protected Telegram updates with replay protection.

Сначала разрешается реализовать Telegram handlers напрямую через application services без полноценной публичной REST API. Все endpoints — целевые, а не обещание полного выполнения в R0.

## 9. Безопасность и доверие

- Хранить только минимальные Telegram identifiers, контактную и адресную информацию; явная privacy notice и retention сроки; возможность экспорта/удаления в пределах обязательств по учёту.
- Не хранить пароли Госуслуг, mos.ru, банков, платёжных провайдеров.
- Изоляция счетов по `account_id` и `property_id`; проверка принадлежности на **каждом** запросе, а не только в интерфейсе.
- Telegram update signature/secret проверять на ingress; token не выводить в логах; signed URLs краткосрочные.
- Перед внешней отправкой OCR проверить применимое основание обработки, регион хранения/передачи данных; российское и международное законодательство оценить отдельно до массового запуска.
- Никакой AI-автоматической отправки окончательных долговых требований без подтверждения пользователя и контроля частоты.
- Backups, восстановление и audit logs с первого коммерческого релиза.

## 10. Тесты и критерии выпуска

### Детерминированные тесты ядра (must pass)
- 125−120 = 5 м³; 5 × 65 RUB = 325 RUB; валютное округление корректно.
- Нулевой расход; отрицательный расход; пропущенный тариф; неполный набор обязательных показаний.
- Изменённый задним числом тариф не меняет утверждённый bill snapshot.
- Дубли Telegram updates, два конкурентных approve, retry worker → один счёт, одно логическое уведомление (физический retry Telegram может доставить дубль: нужен dedup/outbox strategy).
- Чужой арендатор не видит объект; истёкший invite не работает.
- Ошибка после утверждения → корректировка, не редактирование истории.

### OCR evaluation
- Golden set: минимум 50 согласованно обезличенных фотографий различных счётчиков (блики, поворот, нечеткость, красные дробные цифры).
- Метрика: доля верно извлечённых показаний; отдельно false confident errors. На первых пилотах каждое значение подтверждает человек.
- Не выпускать авто-подтверждение по confidence, пока данные не доказывают безопасность порога.

### Acceptance demo R0
1. Собственник создал квартиру/3 счётчика/тарифы.
2. Арендатор по invite вошёл в Telegram-бота и прислал 3 фотографии.
3. Подтвердил/исправил показания.
4. Собственник увидел три строки с расходом/стоимостью и одобрил расчёт.
5. Арендатор получил сообщение; собственник пометил оплату.
6. При повторе команды/доставки не возникло второго начисления.

- Предложить платный план только после наблюдения реального использования; отдельно тестировать цену на квартиру и пакет для управляющего.
- Gate к Manager: хотя бы 3 управляющих готовы дать реальные обезличенные Excel/PDF образцы и согласны обсуждать платный пилот.

## 13. Решения, которые следует принять до первого commit

1. Каноническое название/домен проекта; временно `rentflow`.
2. Валюта/период пилота: RUB, календарный месяц или период фактических показаний (уточнить).
3. Явно закрепить, входит ли водоотведение в платёж арендатора (по умолчанию **нет**).
4. Кто задаёт тарифы и как подтверждается их действительность (в R0 собственник вручную).
5. Чьи фото можно передавать внешнему OCR, политика согласия/хранения.
6. Оплата отмечается вручную собственником; бот не заявляет, что деньги получены, до этого действия.

Начни с репозитория, docker-compose PostgreSQL, migrations и доменных модулей property/tenancy/meter/reading/tariff/bill. Сначала напиши тесты для детерминированного billing engine и idempotent bill approval. Затем Telegram onboarding и приём фото; OCR через заменяемый trait, с обязательной ручной коррекцией. Не реализуй международные интеграции, web portal, платёжный процессинг, PDF-import и настройки произвольных услуг на первом этапе. Не выдумывай существующие Quark APIs; если решил переиспользовать код, сначала исследуй фактические контракты и запиши TODO. После каждого вертикального среза прогоняй тесты. В конце дай инструкцию local run, env.example, миграции, acceptance сценарий и известные ограничения.

## 15. Non-goals и принцип выпуска

**Главная метрика R0:** собственник получает верный, подтверждённый расчёт за минуту активных действий, не пересчитывая цифры вручную. Не обещать «за минуту» как SLA до замеров.

**Фокус:** один вертикальный сценарий от реального фото до отправленной суммы. Всё остальное откладывается до первых пользователей.
